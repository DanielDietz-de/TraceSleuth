# PCAP data sensitivity

## Purpose

Packet captures can contain the actual content of enterprise communications. TraceSleuth is local-first, but local processing does not make packet data harmless.

This document describes the sensitivity assumptions for captures, analysis databases, reports, packet exports, evidence mini-PCAPs, logs, backups, test fixtures, and troubleshooting artifacts.

## What a packet capture may contain

Depending on protocol, encryption, capture point, and snap length, a PCAP or PCAPNG file may expose:

- usernames and passwords;
- HTTP authentication values;
- bearer tokens and API keys;
- cookies and session identifiers;
- Kerberos, NTLM, LDAP, SMB, and other authentication exchanges;
- DNS names and internal namespaces;
- internal and public IP addresses;
- MAC addresses and device identities;
- email, messaging, file-transfer, and application content;
- SIP signaling and RTP media;
- database queries;
- files or file fragments;
- personal data;
- customer or employee information;
- proprietary business data;
- network topology;
- security-control locations;
- VPN/tunnel metadata;
- cryptographic handshakes;
- decrypted content when external key-log material is supplied.

Even when payloads are encrypted, metadata can reveal relationships, service names, destinations, timing, volume, certificates, protocol choices, and behavioral patterns.

## Default privacy principle

TraceSleuth should collect and retain only what is necessary for the operator's analysis workflow.

The product mission requires:

- no automatic PCAP upload to external services;
- no mandatory telemetry;
- no required cloud analysis;
- explicit documentation of optional external integrations;
- configurable retention;
- user-controlled deletion;
- evidence references that avoid duplicating complete payloads into every finding.

Not all of these controls are complete in `0.1.0`; unfinished controls remain explicit roadmap items.

## Original captures

Original captures should be treated as the highest-sensitivity input artifact.

Required target behavior:

- internal random storage identifiers;
- original filename retained only as display metadata;
- restrictive filesystem permissions;
- configurable retention period;
- aggregate storage quota;
- deletion through UI/API/CLI where supported;
- clear documentation of whether originals are retained;
- no silent indefinite retention by default for supported production modes.

## PCAPNG metadata

PCAPNG can contain interface names, descriptions, operating-system details, comments, names, capture-tool information, and other metadata.

TraceSleuth must treat PCAPNG metadata as untrusted input and sensitive content. It should not blindly render active content or use metadata strings as filesystem paths.

## Findings and reports

A report may reveal:

- device identities;
- IP/MAC addresses;
- VLANs;
- DNS names;
- packet timestamps;
- flow metadata;
- packet header values;
- evidence packet numbers;
- security findings;
- inferred topology.

Reports should not include application secrets or full payloads unless the user explicitly requests an export and the feature is documented accordingly.

## Evidence mini-PCAPs

An evidence-only PCAP is still a packet capture. It may contain credentials or personal data.

Evidence export requirements:

- use exact original packets;
- do not silently modify payloads;
- include only packets selected by the documented evidence rule;
- make export scope visible;
- preserve timestamps and packet bytes where technically possible;
- warn that the export remains sensitive.

## TLS key-log and decryption material

NSS-style key-log files and similar key material can permit decryption of otherwise protected sessions.

Treat them as secrets.

Target requirements:

- never write key material to logs;
- restrict filesystem permissions;
- define retention separately from ordinary capture data;
- do not include key material in reports or support bundles;
- delete according to explicit policy.

## Logs

Logs must not intentionally contain:

- passwords;
- bootstrap secrets;
- bearer tokens;
- API keys;
- JWT signing secrets;
- complete sensitive payloads;
- TLS key-log content.

The `0.1.0` bootstrap removed inherited logging of universal default credentials.

Filenames, paths, IP addresses, DNS names, and error messages may also be sensitive. Operators should secure logs and configure retention accordingly.

## Test fixtures

Do not commit private customer or production captures to the public repository.

Preferred fixtures are:

- synthetic;
- minimal;
- generated by documented tooling;
- accompanied by expected and forbidden findings;
- licensed for redistribution.

Third-party captures require verified redistribution rights and documented origin.

## Backups

A backup containing TraceSleuth data may include original captures, reports, histories, user databases, configuration, and key material.

Backup documentation must state:

- what is backed up;
- where data resides;
- encryption expectations;
- retention;
- restore behavior;
- whether deletion in TraceSleuth also removes historical backups.

## External integrations

Optional integrations such as ticketing, threat intelligence, geolocation, or future AI explanations must document exactly which data leaves the TraceSleuth host.

The absence of an external integration must not disable core PCAP analysis.

## GeoIP

If a GeoIP database is embedded or downloaded, documentation should state:

- source/provider;
- license;
- update mechanism;
- whether lookups are local;
- whether any network request is made during analysis.

Core diagnosis must not require an online GeoIP request.

## Deletion and retention

Target configuration should cover:

```text
capture retention period
report retention period
temporary-file retention
maximum aggregate storage
cleanup interval
retain originals yes/no
```

Deletion must fail visibly when artifacts cannot be removed.

The inherited `0.1.0` baseline still retains captures until manual job deletion; this is documented as unresolved hardening work.

## Access control

Localhost-only binding reduces network exposure but is not a substitute for filesystem protection or secure authentication.

For supported non-loopback deployments, TraceSleuth requires a documented authentication, TLS termination, reverse-proxy trust, secure-header, CORS, and CSRF posture before being described as production-ready.

## Incident response

If packet captures or reports are exposed:

1. identify affected artifacts and time range;
2. identify whether captures contained reusable credentials/tokens;
3. rotate exposed secrets where necessary;
4. preserve appropriate forensic evidence;
5. remove unintended public copies;
6. inspect backups and exports;
7. document the exposure path;
8. add a regression control when the product contributed to the exposure.

## Operator responsibility

TraceSleuth helps diagnose network behavior. It cannot determine every legal, regulatory, contractual, privacy, works-council, or data-classification requirement applicable to an operator.

Operators must ensure they are authorized to capture, store, inspect, export, and share the traffic they analyze.
