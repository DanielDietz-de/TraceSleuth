# Threat model

## Purpose

TraceSleuth processes attacker-controlled binary packet captures, stores potentially confidential network traffic, exposes local and future self-hosted web/API interfaces, and generates reports/exports. This document identifies trust boundaries, assets, threat actors, abuse cases, controls, and remaining risks.

This is a living engineering threat model, not a claim that TraceSleuth `0.1.0` is production-ready.

## Security objectives

TraceSleuth should:

1. parse malformed captures without uncontrolled panic or unsafe allocation;
2. prevent path traversal and unsafe filesystem use;
3. prevent unauthorized access to captures, findings, reports, and administration;
4. avoid universal default credentials or predictable secrets;
5. bound CPU, memory, disk, goroutines, analyses, and connections;
6. avoid leaking credentials, tokens, payloads, or key material through logs;
7. preserve local-first operation without mandatory external data transfer;
8. provide explicit retention and deletion behavior;
9. make security failures visible rather than silently degrading;
10. reduce supply-chain risk through controlled dependencies and CI scanning.

## Assets

High-value assets include:

- original PCAP/PCAPNG files;
- packet payloads;
- PCAPNG comments/interface metadata;
- analysis results;
- evidence packet references;
- evidence mini-PCAPs;
- reports and exports;
- user credentials and password hashes;
- JWT signing material;
- active sessions/tokens;
- TLS key-log/decryption material where supplied;
- configuration;
- integration credentials;
- local database;
- topology and internal addressing information;
- build/release integrity.

## Threat actors and failure sources

Potential sources include:

- unauthenticated remote attackers in a self-hosted deployment;
- authenticated low-privilege users;
- malicious capture submitters;
- compromised browser sessions;
- local users on a shared host;
- malicious or compromised dependencies;
- compromised CI/release credentials;
- accidental operator misconfiguration;
- malformed capture files generated by bugs rather than adversaries;
- oversized legitimate captures that exhaust resources.

The threat model does not assume every malformed packet is malicious. Robustness and security controls should handle both intentional and accidental bad input.

## Trust boundaries

### Boundary 1: capture ingestion

Untrusted inputs:

- PCAP bytes;
- PCAPNG bytes;
- uploaded filename;
- MIME metadata;
- file extension;
- request body size;
- capture comments;
- interface names/descriptions;
- future compressed archives if ever supported.

Required controls:

- content/magic validation;
- streaming byte limit;
- generated internal IDs/names;
- path containment;
- bounded lengths before allocation;
- no trust in filename as path;
- explicit format errors;
- cleanup on partial failure.

### Boundary 2: packet and protocol parsing

Untrusted data:

- lengths;
- offsets;
- option/TLV lengths;
- nested encapsulation;
- fragmented content;
- malformed headers;
- intentionally adversarial packet sequences.

Required controls:

- length checks;
- integer overflow review;
- bounded allocation;
- no routine panic;
- panic recovery at appropriate trust boundaries;
- malformed counters;
- fuzzing;
- regression fixtures.

### Boundary 3: analysis engine

Threats:

- unbounded maps;
- pathological flow cardinality;
- excessive fingerprint state;
- expensive detector combinations;
- goroutine explosion;
- cancellation failure;
- race conditions;
- nondeterministic output;
- crafted captures maximizing CPU.

Required controls:

- bounded state;
- global maximum concurrent analyses;
- per-analysis deadlines;
- context cancellation;
- bounded workers/queues;
- rate/resource metrics;
- expensive-detector disablement;
- race testing;
- benchmarks/adversarial workload tests.

### Boundary 4: storage

Threats:

- path traversal;
- unsafe symlinks;
- permissive modes;
- indefinite retention;
- disk exhaustion;
- orphaned temporary files;
- deletion failures;
- backup leakage.

Required controls:

- generated internal paths;
- restrictive permissions;
- dedicated data/temp directories;
- retention policy;
- aggregate quota;
- safe deletion;
- no silent retention forever in supported production mode;
- explicit backup behavior.

### Boundary 5: authentication and authorization

Threats:

- universal credentials;
- weak bootstrap behavior;
- predictable JWT secrets;
- token theft;
- disabled-user token reuse;
- role bypass;
- brute force;
- query-string token leakage;
- session lifetime abuse.

Current bootstrap controls:

- no universal `admin/admin` creation;
- explicit bootstrap variables;
- bcrypt password hashing;
- no bootstrap password logging;
- CSPRNG-generated JWT key material;
- fail-closed behavior on CSPRNG failure;
- role checks;
- active-user validation.

Remaining work:

- complete WebSocket token hardening;
- session revocation design;
- secure cookie option if adopted;
- first-run UX;
- brute-force/rate-limit validation;
- supported non-loopback deployment contract.

### Boundary 6: HTTP/API/UI

Threats:

- CSRF;
- CORS misconfiguration;
- clickjacking;
- XSS through packet metadata or filenames;
- content sniffing;
- unsafe report rendering;
- excessive WebSocket connections;
- unbounded request bodies;
- reverse-proxy header spoofing;
- sensitive caching.

Required controls:

- restrictive CORS;
- CSRF protection where cookie-authenticated state changes exist;
- output escaping;
- security headers;
- request/body limits;
- connection limits;
- explicit trusted-proxy configuration;
- TLS termination guidance;
- no claim of built-in production TLS unless implemented/tested.

### Boundary 7: reports and evidence export

Threats:

- sensitive payload disclosure;
- path traversal;
- formula injection in CSV;
- active HTML content;
- oversized export generation;
- exporting more packets than shown as evidence;
- temporary-file leakage.

Required controls:

- explicit export scope;
- exact original packet preservation;
- safe filenames;
- bounded export size/time;
- escaping/sanitization by format;
- sensitive-data warnings;
- cleanup.

### Boundary 8: external integrations

Potential integrations include:

- threat intelligence;
- ticketing;
- GeoIP updates;
- future optional AI explanation;
- external authentication/reverse proxy.

Threats:

- accidental PCAP/payload exfiltration;
- credential leakage;
- SSRF;
- malicious responses;
- availability dependency;
- privacy ambiguity.

Required policy:

- core analysis remains offline;
- external integrations are explicit and optional;
- document exactly what data leaves the host;
- do not send PCAPs externally by default;
- use timeouts and response limits;
- protect integration credentials.

### Boundary 9: build and supply chain

Threats:

- vulnerable dependencies;
- malicious dependency updates;
- compromised GitHub Actions;
- overbroad workflow permissions;
- leaked release token;
- unsigned/unverifiable artifacts;
- version drift.

Current controls:

- Go module checksums;
- npm lockfile;
- `npm ci`;
- `govulncheck`;
- CodeQL;
- Gitleaks;
- least-privilege workflow permissions where practical;
- authoritative `VERSION`;
- release tag/version validation;
- SHA-256 checksums.

Remaining work:

- SBOM;
- artifact provenance/signing when infrastructure exists;
- action SHA pinning policy;
- container scan for production image;
- dependency review;
- reproducibility characterization.

## Abuse cases

### Malicious capture claims enormous packet length

Risk:

- allocation exhaustion;
- integer overflow;
- parser panic.

Expected control:

- validate record/block lengths before allocation;
- cap resources;
- fuzz boundaries;
- return useful error.

### Filename attempts path traversal

Example:

```text
../../authorized_keys
```

Risk:

- overwrite arbitrary files.

Expected control:

- use generated internal storage names;
- original filename is display metadata only;
- enforce directory containment.

The baseline audit identifies inherited filename/path construction as unresolved in `0.1.0`.

### Duplicate-capture input triggers false loop diagnosis

Risk:

- operationally dangerous false positive;
- engineer disables healthy ports.

Expected control:

- capture duplication runs before loop diagnosis;
- stable duplicate factors and near-zero inter-copy delays reduce/suppress relevant confidence;
- adversarial SPAN/broker fixtures.

This is both a correctness and safety threat even if it is not a conventional confidentiality vulnerability.

### Capture causes unlimited flow/fingerprint state

Risk:

- memory exhaustion.

Expected control:

- bounded detector state;
- eviction/summarization;
- resource limits;
- performance tests.

### Attacker reuses stolen WebSocket query token

Risk:

- token leakage through logs/history/intermediaries.

Expected control:

- remove query-token dependency in supported production mode;
- use safer authentication transport;
- short-lived/session-aware tokens where appropriate;
- avoid logging credentials.

### Operator binds insecure server publicly

Risk:

- unauthorized access;
- cleartext credentials/tokens if TLS absent;
- exposure of PCAP data.

Expected control:

- secure defaults;
- no universal credentials;
- explicit non-loopback deployment requirements;
- reverse-proxy TLS documentation;
- startup safeguards where appropriate.

## Security invariants

The target architecture should preserve these invariants:

```text
No universal administrator password.
No hard-coded fallback signing secret.
No original upload filename used as trusted filesystem path.
No unbounded upload stream.
No silent indefinite capture retention in supported production defaults.
No mandatory PCAP upload to external services.
No secret/token/password logging.
No claim that a scanner passing proves security.
No critical heuristic diagnosis from weak evidence alone.
```

## Current status by risk

### Addressed in bootstrap branch

- universal `admin/admin` first-run credential removed;
- hard-coded JWT fallback secret removed;
- bootstrap password no longer logged;
- CI/security scanning foundation added;
- changed-file repository hygiene gate added.

### Known unresolved high-priority risks

- uploaded filename/path hardening;
- configurable retention and storage quota;
- global concurrent-analysis limit;
- analysis timeout/cancellation propagation;
- complete parser fuzzing;
- capture-quality preflight;
- WebSocket query-token handling;
- secure headers/CSRF/CORS review;
- supported non-loopback deployment contract;
- full temporary-file and export review.

See the baseline audit and roadmap.

## Validation strategy

Security controls require:

- unit tests;
- malformed-input tests;
- regression tests;
- fuzzing;
- race tests;
- integration tests;
- static analysis;
- dependency vulnerability scanning;
- adversarial resource tests;
- manual design review for high-risk boundaries.

Do not silence failing tests or scanners merely to make CI green.

## Out of scope for the threat model

This document does not determine:

- legal authorization to capture traffic;
- every jurisdiction's privacy law;
- contractual data restrictions;
- organizational classification policy;
- whether an operator's network architecture is safe.

Operators remain responsible for lawful capture and secure handling.

## Review cadence

Review this threat model when:

- a new input format is added;
- compressed uploads are introduced;
- a parser is added;
- server binding/authentication changes;
- a new external integration is added;
- AI explanation features are introduced;
- container/systemd deployment becomes supported;
- a serious vulnerability is fixed;
- stable 1.0 release validation begins.
